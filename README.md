# Healthcare Data Validation (SQL, Snowflake / Databricks)

SQL data-quality checks for healthcare data (patients, encounters, claims), the kind of
validation that should run **before data is delivered to a client**.

> **Data note:** the dataset is **synthetic**, generated by `data/generate_data.py`. No real patient
> data is used. The generator deliberately injects realistic problems (blanks, duplicates, bad
> dates, orphan records, impossible amounts, a volume drop), so every check has something to catch.

## What it checks (23 checks)

| Category | Examples |
|---|---|
| Completeness | missing birth_date, gender, patient_id, encounter_id, billed_amount |
| Uniqueness | duplicate patient_id / encounter_id / claim_id |
| Data types | non-date values in date columns (`2026-02-30`), non-numeric amounts (`N/A`) via `TRY_CAST` |
| Accuracy | invalid gender, birth date in the future, discharge before admission, negative billed amount, paid > billed, bad status, malformed ICD-10 code |
| Relationships | encounters with unknown patients, claims with unknown encounters, claim patient differs from encounter patient |
| Trends | daily encounter volume < 50% of trailing 7-day average (simulated pipeline outage) |

Each check returns `failed_rows`, `total_rows`, `fail_pct` and `PASS/FAIL`. A separate drill-down query
(`sql/02_trend_anomaly_detail.sql`) shows exactly which days dropped.

## Project layout

```
data/generate_data.py          creates patients.csv, encounters.csv, claims.csv (+ injected_issues.json)
sql/01_validation_checks.sql   all 23 checks in one portable query
sql/02_trend_anomaly_detail.sql  which days had a volume drop
run_checks.py                  run everything locally with DuckDB, writes results/dq_report.csv/.md
snowflake/setup_and_run.sql    load CSVs into Snowflake and run the checks
databricks/run_checks_notebook.py  Databricks notebook version
```

## How to run

**1. Locally (easiest, 2 minutes)**
```
pip install duckdb
python data/generate_data.py
python run_checks.py
```

**2. Snowflake (free trial):** follow `snowflake/setup_and_run.sql`.

**3. Databricks (free edition):** follow the steps at the top of `databricks/run_checks_notebook.py`.

The SQL is written to be portable (`TRY_CAST`, `REGEXP_LIKE`, window functions); if a function name
differs on your platform, that is the first place to look.

## Expected result

On the generated data, 20 of 23 checks fail (the three that pass are `status` values, `paid_amount`
type and `encounter_id` uniqueness, because those problems were not injected). Compare the counts with
`data/injected_issues.json`: they match closely. Small differences are real and explainable: rows that
were duplicated also duplicate their own issues, and a negative billed amount also makes `paid > billed` true.

## Interview talking points (be ready to explain each one)

- **Why load everything as VARCHAR?** So type problems are detected by the checks instead of silently
  failing or being coerced at load time.
- **Why `TRY_CAST` instead of `CAST`?** `CAST` errors on the first bad value and stops the whole query;
  `TRY_CAST` returns NULL, so I can count bad values.
- **Why blank vs NULL?** CSV loads often turn missing values into empty strings, so completeness checks need to test both.
- **Why a relationship check on patient_id in claims vs encounters?** A claim can reference a valid encounter
  but belong to the wrong patient, which a simple "key exists" join misses.
- **How does the trend check work?** Window function: average of the previous 7 days, flag days under 50%. It catches
  silent pipeline failures where data still arrives but a lot is missing.
- **What would you do next?** Schedule the checks (Snowflake Tasks / Databricks Workflows), store results in a
  table, alert on new FAILs, and add thresholds per check instead of "any failure".
